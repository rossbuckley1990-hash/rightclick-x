7. INTEGRATE ACTENON WITHOUT REINVENTING IT
========================================================

The Actenon ecosystem already provides relevant
authority infrastructure.

Inspect:

https://github.com/Actenon/actenon-kernel
https://github.com/Actenon/actenon-permit
https://github.com/Actenon/actenon-protocol
https://github.com/Actenon/actenon-airlock
https://github.com/Actenon/actenon-scan

Reuse the existing Actenon work where technically
appropriate and compatible.

Do not introduce duplicate cryptographic formats.

Do not create another permission framework without
a demonstrated requirement.

The desired principle is:

OPEN-ENDED DISCOVERY.
EXACT-ACTION AUTHORITY.

A newly discovered operation does not inherit
permission to execute.

A composed workflow does not gain additional
authority simply because its individual operations
appear available.

A repaired workflow does not automatically inherit
the original proof for a changed action.

Where protected execution is enabled:

- Permit must evaluate actual authority.
- The execution edge must verify the appropriate proof.
- The proof must bind the actual target and parameters.
- Credentials must remain outside agent control.
- Revocation must affect subsequent execution.
- Replay protection must remain effective.
- Uncertain consequential effects must not be blindly
  retried.

CRITICAL:

A protected route does not guarantee containment
if the agent has an alternative unprotected route.

Demonstrate the relevant boundary independently.

Do not imply Actenon protects model output,
prevents every prompt injection or controls arbitrary
operating-system actions.

If Actenon integration is incomplete, show
AUTHORITY NOT ESTABLISHED rather than fabricating
an approval.

Actenon integration should be optional for ordinary
local read-only experimentation.

Consequential operations configured as protected
must fail closed when the required authority service
or protected edge is unavailable.
